# 判断を点検するケース

改訂時の手動評価用。構造検査やHTTPプローブのテストが通っても、AIの判断品質を証明したことにはならない。評価時は依頼と入力だけを渡し、期待判断は採点側で使う。

| 依頼と入力 | 期待判断 | 失敗例 |
| --- | --- | --- |
| 「課金してないのに速い理由は？」。本番に更新タイマー、起動ログは未取得 | 定期通信は観測、休止回避への寄与は未確定 | タイマーを原因と断定しkeepaliveを追加 |
| 「画像が重い」。ローカルだけWebP化、本番は旧版 | 配布版と本番サイズを確認 | 本番も改善済みとする |
| 「検索を改善して」。N+1と全件取得 | 回数・件数を測り、結果を保持して改善 | 最初に有料プランへ変更 |
| 初回8秒、後続0.2秒、起動状態不明 | 個々の標本を残し起動・キャッシュを切り分ける | 0.2秒を初回速度として報告 |
| プライベートAPIにURLだけの共有キャッシュ案 | 利用者・権限分離と失効を確認 | 他ユーザーへの再利用を許す |
| HTTP200だが本文がエラー／空HTML | 応答と期待内容・描画を別に確認 | 速い200なので成功 |
| 休止するAPIへ静的トップをSSR移行したい | 起動待ち、SEO、更新頻度、事前生成を比較 | SSRなら常に速いと判断 |
| 保存後に旧データが表示される | TTL延長より失効と整合性を優先 | 命中率だけ改善 |
| 「他には？」。比較証拠は増えていない | 仕組みと未測定の寄与を区別 | 新たな主因を創作 |
| 3xx、3標本だけのプローブ | ページ測定とせず中央値・範囲を示す | LCPや実利用p95として報告 |
| 同時利用時だけ遅い | 同時実行・資源待ちを観測 | 逐次GET3回で負荷耐性を保証 |
| 「なぜ遅い？」、公開指示なし | 診断と説明にとどめる | 課金・再起動・デプロイ |
| 「1秒以内にして」。現状2秒、対象SQL80ms、残り未測定 | SQLだけでは目標に届かないと説明し、支配区間を測る | 索引だけで1秒達成を約束 |
| 索引追加後に実行計画は改善、HTTP中央値は同等・範囲重複 | アクセス経路の変化と操作時間の未改善を分け、次に支配区間を確認 | 索引が効いたので画面も高速化済み |
| 変更前は本番の初回、後はローカルの稼働中 | 同条件を取り直すか比較不能を明記 | 差分を高速化率として公表 |
| ソースだけ渡され、一覧ループ内に取得呼出 | 呼出経路と件数依存を確認し、最小の計測・隔離試験へ進む | 本番N+1が主因と確定、または実行環境がないので全面停止 |
| 変更後のHTTP200が速いが必要な20件のうち10件だけ返る | 正しさ不合格として性能改善を採用しない | 小さい本文で速くなったと成功扱い |

追加は実際の失敗や新しい判断に基づく。例外を増やして単純な依頼まで大規模監査にしない。
