# Web速度改善

利用者の待ち時間を減らす。特定のホスティング、フレームワーク、有料プランを前提にせず、遅い経路を特定してから対策を選ぶ。

成果は「どの操作が、正しい結果を保ち、どの条件で何秒変わったか」。初動では遅い操作を一つ再現し、その操作の待ち時間を説明できる測定を選ぶ。プロジェクト固有の計測がなければ、[最初の観測から対策まで](references/diagnosis.md)から入る。

## 依頼に合わせる

- 「なぜ速い／遅い？」には調査と説明。「改善して」には実装と検証まで進める。「他には？」で根拠のない原因を足さない。
- 現在のソース、対象URL、配布版、API接続先、実行環境を確認する。ローカルの改善を本番の速度の理由にしない。
- 既存の計測や変更履歴を先に使う。診断だけの依頼で契約変更、再起動、キャッシュ削除、デプロイをしない。公開や課金の権限は既存の依頼から判断する。
- 全項目の監査を毎回始めず、症状に関係する経路を絞る。参照資料も必要なものだけ読む。

## 測定から改善へ

1. **操作を定める。** 最初の表示、再訪問、ページ移動、検索、詳細表示、保存のどれか。表示速度と保存完了までの時間を混ぜない。
2. **比較条件を残す。** 配布版、端末・回線、ログイン、データ量、キャッシュ、起動状態を記録する。取得できない条件は不明とする。[測定手順](references/measurement.md)を参照する。
3. **待ち時間を分解する。** 配信／起動待ち → API・DB → 画像・JS取得 → 描画・操作反応。ウォーターフォール、トレース、クエリ計画など、仮説を区別できる証拠を使う。
   並行している時間を単純加算しない。利用者が待つ経路をたどり、支配的な区間と、その区間を減らしても残る待ち時間を示す。例えば表示2秒のうち対象SQLが80msなら、SQLだけで1秒短縮する案にはしない。
4. **対策を選ぶ。** [改善の判断表](references/interventions.md)で症状と対策を対応させる。キャッシュ・先読み・定期通信を変える場合は[鮮度と起動状態](references/cache-and-lifecycle.md)を読む。
5. **変更して比較する。** 効果が見込める箇所から、因果を追えるまとまりで変更する。アクセス権、更新反映、検索結果、保存結果を確認し、同条件で再測定する。効果が出なければ仮説を見直す。

## 誤った結論を防ぐ

- 最適化コードの存在は、その環境で実行された証拠でも、今回の改善原因の証明でもない。比較できない場合は「仕組みは確認済み、寄与は未測定」と説明する。
- 自分の測定がサーバーを起動し、キャッシュを温める。後続の速さを、初回アクセスや終日安定性の証明にしない。
- 定期通信があることだけで、休止回避の原因と断定しない。ブラウザの休止、通信先、実際のアクセスログを照合する。
- HTTPの成功、期待データの取得、正しい画面表示、業務の完了を分ける。空のHTMLやエラー本文が速く返っても改善とはしない。
- キャッシュで速くなっても、別ユーザーの情報露出、更新の遅れ、承認取り消し後の表示を許容しない。
- サーバー増強は解決対象を示して提案する。価格・制限は対象サービスの公式資料でその都度確認する。課金すれば全処理が速くなるとは説明しない。

## 完了の示し方

依頼に見合う長さで、改善点／比較条件と結果／未確認の制限／反映先を伝える。

| 操作・条件 | 変更前 | 変更後 | 分かったこと |
| --- | --- | --- | --- |
| 同一条件の比較 | 実測値・試行数 | 実測値・試行数 | 計測で支持される結論のみ |

小標本の中央値・範囲を、多数の利用者のp95や保証値として扱わない。測定できなかった項目は数値を作らない。改善が不要ならその判断で止め、追加の最適化を必須作業にしない。

## 補助ツールと自己点検

- [HTTPプローブ](scripts/http_probe.py)：認証不要で副作用のないURLの小規模な連続測定。ブラウザ速度や負荷試験の代わりにはならない。[測定手順](references/measurement.md)を読んで使う。
- [前後比較](scripts/compare_http.py)：同じ期待本文・申告条件を持つ測定JSONを比較。欠損、失敗、内容不一致を含む測定では速度差の結論を拒否する。条件ラベルが同じでも実環境の一致は別途確認する。
- [再現実験](scripts/demo_index.py)：SQLiteの索引追加を、独立した期待結果・実行計画・前後のHTTP標本で検証する。手元で道具の動作を確かめる場合だけ実行し、通常の案件にデモ実行を追加しない。
- [検証ケース](references/validation-cases.md)：改訂時や判断に迷うときに使う。通常の依頼で全ケースを実行しない。

# キャッシュの鮮度、権限、起動状態

## キャッシュ前に決める

対象データ、キー、保持期間、更新契機、破棄条件、最大容量を決める。ブラウザ・CDN・API・DB周辺は別々に扱う。

- キーに検索条件・ページ・並び順・言語・ユーザー／テナントなど、結果を変える条件を含める。公開キャッシュに個別の認証情報を入れない。
- TTLだけでよい情報と、保存・削除・公開取り消し・権限変更時に即時失効させる情報を分ける。「営業時間中」のような時刻依存データにも注意する。
- 署名付きURLのキャッシュは残り有効期限を越えない。URLが有効でも公開取り消し後の表示を許してよいとは限らない。
- 失敗や空の代替表示を長期間キャッシュしない。古いデータを表示するなら、データの性質に合わせて期限と表示方針を決める。
- 同時要求をまとめてもユーザーをまたがず、失敗後に再試行できるようにする。
- メモリキャッシュはプロセスごとに異なり、再起動で消える。複数インスタンスでも必要な失効が届くか確認する。

## 先読み

よく使う結果や次に見るデータの先読みは、頻度と負荷が見合う場合に限る。起動時の大量先読みで起動時間やDB負荷を増やさない。遅延画像をJavaScriptで一括取得しない。データの先読みと画像差し替え時の事前読み込みは別の動作として確認する。

## 定期通信と起動待ち

ブラウザの更新タイマー、管理画面、監視、検索ボット、外部連携の要求先と頻度を調べる。

「60秒タイマーがある」から「サーバーが休止しない」とは断定できない。別サービス宛てかもしれず、非表示・端末スリープで抑制される場合もある。提供元の休止条件、到着ログ、再起動時刻を対応させる。

更新目的なら必要な鮮度に合わせた間隔、非表示時停止、フォーカス時更新、バックオフを検討する。通信を減らした結果、無料環境で起動待ちが増える可能性は明示する。常時稼働が必要なら、不要な通信で制限を回避する案ではなく要件に合う契約・構成を比較する。

## 変更に関係する動作を確認

- 未ログイン／ログイン／別ユーザー／別テナントで正しい情報が返る。
- 保存、削除、承認取り消し、ログアウト後に古い情報が漏れない。
- TTLや署名期限を越えた後に再取得できる。
- 同時要求、通信失敗、再起動、複数インスタンスで不整合を増やさない。
- 初回と再訪の差を説明できる。キャッシュ命中時だけを成果にしない。

# 最初の観測から対策まで

「遅い」を利用者の操作に置き換える。例: 検索ボタン押下→正しい20件が表示され操作可能になるまで。現状を再現し、終了点と結果を決めてから最適化する。既存の計測が十分なら再作成しない。

## 次に何を取るか

| 最初の証拠 | 次の観測 | 判断が変わる点 |
| --- | --- | --- |
| HTMLの取得自体が長い | 同じ要求IDのサーバー区間、起動ログ、DB時間 | 接続・起動待ちか、要求処理か |
| HTML/APIは速いが画面が遅い | ブラウザのネットワークとメインスレッドの同一操作トレース | 転送・依存する要求の連鎖か、JS処理・描画か |
| APIの件数を増やすと遅くなる | 20件と100件のDB要求数・返却バイト数・結果 | N+1、全件取得、CPU計算のどこが伸びるか |
| 単独では速く同時利用で遅い | 既存負荷ログの待機時間、接続数、CPU | 資源待ちか処理時間増加か。逐次GETでは判定しない |
| 初回だけ遅い | 初回と後続を別記録し、起動記録とキャッシュ命中を照合 | 計測自身が温めた結果を改善にしない |

ブラウザ操作の権限や道具がないときは、HTTPの測定範囲を示してアプリ側のトレース等で調べる。ブラウザを測れていないことを全調査の停止理由にせず、HTTP時間を画面時間に置き換えない。

## ソースしか読めない場合

画面操作→イベント→取得関数→API→DBの呼出経路を一つ追い、次の兆候を確認する。コードだけで実行頻度や本番の寄与は確定しないが、計測する箇所と局所修正案は具体化できる。

| コードの兆候 | 静的に確認するもの | 確定に必要な最小の観測 |
| --- | --- | --- |
| 一覧ループ内のDB/API呼出 | 呼出回数が件数に依存する経路、キャッシュやバッチの有無 | 件数を変えた要求数と処理時間 |
| 取得後にslice/filter | SQLのLIMIT・WHERE、取得カラム、総件数計算 | DB取得件数・返却バイト・実行計画 |
| 独立処理の連続await | 後続が前の結果を使うか、同時実行上限 | 同じ操作のタイムラインと部分失敗時の結果 |
| state変更ごとのfetch | effect依存値、再描画、キャンセル、要求の重複 | 操作一回に対する実要求数と最新結果の保持 |
| 大きなライブラリの共通import | 実際のentry・bundle、遅延ロード経路 | ビルド出力と初回転送・評価時間 |

実行環境がない場合は「この経路では件数に比例して呼出が増える」「本番の待ち時間への寄与は未測定」のように範囲を保つ。変更が依頼され、隔離テストで結果を確認できるならその範囲まで実装する。必要なログを一括で求めず、結論を変える観測だけを指定する。

## 変更候補を一つに絞る

観測した経路について「証拠→待ち時間を生む仕組み→変更→反証できる試験」を短くつなぐ。推定効果の上限は、対象区間が操作全体に占める時間から考える。重複・並行区間は合計しない。最初から秒数を捏造せず、区間不明ならまずその区間を測る。

目標時間がある場合は、測定したクリティカルパス上で対象区間以外の残る時間を求め、目標から引いて対象区間に許される時間を出す。この値は達成に必要な予算であり、変更すれば実現できる予測ではない。バッチ化・増強後の時間は試作や実測まで不明とする。増強を支持する証拠がないことと、将来も不要であることを区別する。

例: 一覧20件でSQL21回、100件で101回、トレースでは子問い合わせが直列 → バッチ取得 → SQL回数が一定になるか、順序・欠損値・権限・ページ境界を保持するか確認。同じ要求数ならN+1以外を調べる。キャッシュは元の処理が速くなる対策とは区別する。

## 比較を成立させる

変更前を残し、変更後と同じ操作・データ・権限で測る。期待結果は変更前の出力を盲目的に正解扱いせず、仕様か独立したfixtureに照合する。画面では主要内容・操作可能性、APIでは必要な項目・順序・件数を確認する。

初回の改善が重要なら初回条件を別に再現する。安全に条件を戻せないときは、その制限を残す。十分な差が出ても固定順序の前後比較には時刻・負荷・キャッシュが混ざる。重要な因果判断で可逆かつ許可範囲内ならA→B→A、交互測定、または同じ負荷の対照を使う。条件を揃えられない結果を「X%改善」と一般化しない。

速くなっても必要なデータ・権限・更新反映を失えば不合格。効果が出なければ改善と報告せず、残す理由がなければ自分の変更だけ戻す。結果の正しさ、操作全体の時間、運用負担から採用を判断する。

## 完了時に残す最小の証拠

操作と終了点、対象revisionと実行環境、比較条件、期待結果の確認方法、生の標本、採用した変更と結果。既存のIssueや作業報告へ必要量だけ残す。利用者には実測結果と反映先を先に示す。環境が違う結果は別行にする。

# 症状に合わせて改善を選ぶ

| 症状・証拠 | 対策候補 | 判定する観測・副作用 |
| --- | --- | --- |
| 不変ファイルまでアプリサーバーを通る | 静的配信、CDN、ハッシュ付きファイルのキャッシュ | 転送量・配信待ち。HTML更新時の古いJS参照に注意 |
| 毎回同じ公開HTMLを生成する | ビルド時生成、期限付き再生成 | 初回表示と更新反映。個人情報を混ぜない |
| JS取得後も本文が長く出ない | SSR・事前生成・要求依存の削減を比較 | HTML本文とLCP。休止するサーバーへのSSR移行は遅くなる場合もある |
| 一覧で大量の本文・写真・レコードを返す | 必要フィールド、ページ分割、件数制限 | ペイロード・クエリ時間。総件数計算も確認 |
| 件数に比例してDB要求数が増える | JOIN、バッチ取得、集約 | 要求数と結果の整合性。無制限な並列化への置換を避ける |
| 検索クエリが遅い | 条件・並び順に合うインデックス、SQL・統計の見直し | 実行計画。書き込みコストやインデックス作成中のロックも考慮 |
| 独立したAPI・画像署名などが順番待ち | 並列化と同時実行上限 | ウォーターフォール、接続数、レート制限、部分失敗 |
| 接続確立・プール待ちが支配的 | 接続再利用、プール容量と総接続予算の調整 | 待機・接続数。複数プロセスやインスタンスの分も数える |
| 同一データの反復計算 | TTL付きキャッシュ、同時要求の共有 | 命中率、鮮度、権限。キャッシュ資料を参照 |
| 画像転送が重い | 圧縮、WebP/AVIF等、適切な寸法、srcset/sizes | 実バイト数と画質。形式名だけで軽量化を断定しない |
| 画面外画像が最初から大量に競合 | 遅延読み込み、非同期デコード | 主要画像は遅延しない。表示寸法を確保する |
| 主要画像・フォントの発見が遅い | 優先度・preload、フォント削減 | 競合とLCP。何でもhigh/preloadにしない |
| 初期JSに管理・編集・地図機能が混在 | 機能単位の遅延読み込み、依存削減 | 初期JS量と操作時の追加待ち。過度な分割を避ける |
| スクロール・入力が重い | 不要な再描画・長いタスク削減、必要なら仮想化 | 操作トレース。検索性、アクセシビリティ、スクロール位置も保持 |
| ページ移動で全取得・描画を繰り返す | ルーター、状態再利用、必要箇所のみ更新 | 直リンク・戻る・認証変更を確認。無条件にSPA化しない |
| 一部APIが画面全体を止める | 表示単位の分離、段階表示、ローディング表示 | 見えるまでと完了までを分ける。エラーを隠さない |
| 無通信後の最初だけ遅い | 起動ログ・休止条件の確認、常時稼働プランの比較 | 定期通信と実ログ。処理自体の高速化とは限らない |
| 負荷で待機・エラーが増える | ボトルネック改善後、資源増強・構成変更 | CPU・メモリ・DB・同時実行・費用。小規模プローブは負荷試験ではない |

利用者への影響、操作頻度、観測された待ち時間、変更リスク、保守負担で優先順位をつける。期待効果を根拠なく秒数や割合にしない。小さな改善で足りるなら全面刷新に広げない。

SEOと速度は別の結果。事前生成できただけでインデックス登録や順位向上を保証しない。期待する本文・操作・結果が保たれることも確認する。

# 測定と因果の切り分け

## 比較条件

対象の版・URL・操作、時刻と地域、端末・ブラウザ・回線、認証状態、データ規模、キャッシュ条件、起動状態を、判断に必要な範囲で残す。未確認を推測で埋めない。

同じ操作を少数回繰り返し、個々の値と中央値・範囲を見る。最初の試行を隠して平均だけを出さない。初回と再訪、命中と不命中、起動直後と稼働中は別の標本にする。実利用の分布が必要なら、プライバシーに配慮した既存のRUMやログを利用する。

| 調べたいこと | 観測 | 注意点 |
| --- | --- | --- |
| 最初の画面 | Navigation / Resource Timing、FCP・LCP、画面 | APIだけの速度では判断できない |
| 操作への反応 | 操作トレース、長いタスク、INPの実利用データ | 単発の操作時間を集計済みINPと呼ばない |
| API | クライアント計測と要求IDに対応するサーバートレース | ネットワークとサーバー実行時間を分ける |
| DB | クエリ回数、実行計画、待機、接続プール | EXPLAIN ANALYZEは実行を伴う。本番の書き込み・重い処理に注意 |
| キャッシュ | Age等のヘッダー、命中記録、比較条件 | ヘッダーだけで全階層の命中を断定しない |
| 休止後 | 起動ログと最初の実アクセス | 連続測定では本当の休止後アクセスは再現できない |

キャッシュ回避のランダムなクエリ追加は、アプリの条件・SEO処理・DBキャッシュキーを変えることがある。ブラウザのキャッシュ無効化もCDNやDBの無効化とは異なる。

## 小規模HTTPプローブ

Python 3.10以上、追加依存なし。スキルのディレクトリで実行する。

```sh
python scripts/http_probe.py https://example.com/ --count 3 --interval 1
```

- 公開されている読み取り専用URLを指定する。GETでも業務実行やリンクトークン消費を伴うURLには使わない。
- 認証、Cookie、任意ヘッダー、リダイレクト追従には非対応。URL中のユーザー情報は拒否する。クエリに秘密を入れない。
- 最大10回、逐次実行。既定は3回・間隔1秒。タイムアウトは各ソケット操作の上限で、遅いストリーム全体の絶対上限ではない。
- URL・本文・Cookie・生の例外文字列はJSONに出さない。対象識別情報は共有先に合わせて別に記録する。
- `headers_ms` は開始からレスポンスヘッダー取得まで。厳密なTTFBではない。`total_ms` は本文取得完了または上限到達まで。
- 3xxは追従せず記録する。4xx・5xx、通信エラー、本文上限超過を正常標本に混ぜない。完全に取得できた2xxも業務上の成功を保証しない。
- 接続再利用やブラウザキャッシュを再現しない。JavaScriptを動かさず、画像も取得しない。描画、LCP、操作応答や負荷耐性は別に測る。

仮説を区別できる証拠と必要な比較がそろったら止める。原因が未確定なら残る候補と必要な観測を示す。調査を理由に大量アクセスしたり、本番を止めてコールド状態を作ったりしない。

## 正しい本文を保つ前後比較

公開された決定的なレスポンスには `--expect-sha256` で、仕様・fixtureと照合済みの期待本文のSHA-256を指定できる。本文は保存・表示せず、完全な2xxと内容一致を別々に記録する。不一致なら終了コード1。期待値を、合格させるために変更後の出力から作り直さない。

```sh
python scripts/http_probe.py https://example.com/data --count 5 --expect-sha256 <64桁のSHA256> --condition public-fixture-v1-warm --revision before > before.json
# 対象を変更し、同じデータ・操作・起動状態等を確認した後
python scripts/http_probe.py https://example.com/data --count 5 --expect-sha256 <同じSHA256> --condition public-fixture-v1-warm --revision after > after.json
python scripts/compare_http.py before.json after.json
```

`condition` は操作者が確認した条件の識別子であり、自動計測で環境一致を証明する値ではない。実際の端末・データ・キャッシュ・操作等を作業記録に対応させる。revisionも実行版を照合する。秘密情報をこれらの文字列に含めない。

比較は両側3〜10標本、全標本が完全な2xxかつ同一の期待本文と一致、同じ条件ラベル、異なるrevisionの場合だけ記述統計を返す。保存されたsummaryを信用せず生の標本から再計算する。負の変化率は短縮、正は悪化。範囲の重なりも返すが、統計的有意性・因果関係は判定しない。標本が少ないため実利用p95は出さない。

時刻・nonceなどで毎回本文が変わる場合、ハッシュ比較は不適切。プロジェクトの意味的な期待結果テストと計測を使い、JSONの記録を後から書き換えてこのツールを通さない。ハッシュ一致は仕様の正しさそのものの証明でもない。

ローカルの索引実験は `python scripts/demo_index.py`。外部サービスへ接続せず、一時SQLite・ループバックHTTPだけを使う。100,000行の固定データで独立した期待値と照合し、索引前後の実行計画と7標本ずつを返す。`db_execute_fetch_ms` はSQL実行・全行取得だけの時間で、接続確立・JSON生成・HTTP・描画を含まない。HTTP全体の短縮と区別する。固定順序・OSキャッシュ等の影響を含み、出た倍率を他の案件へ転用しない。
